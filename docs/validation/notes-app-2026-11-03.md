## 问题与复现

### I-1（组件，未修复）：Badge Warning 前景在 dark 与高对比度下对比不足

- **复现**：渲染 `Badge::new("未保存").appearance(BadgeAppearance::Warning)`，在 `FluentTheme::web_dark()` 与 `FluentTheme::high_contrast()` 下观察。本轮在应用的工具栏版本中实际看到：HC 为白色胶囊无可见文字，dark 为白字黄底（截图 `notes-long-title.png`、`notes-draft-dark-shown.png`，本地、未提交）。
- **源码依据**：[`spec/feedback.rs` badge](../../crates/fluent-core/src/spec/feedback.rs) 把 Warning 的前景映射到 `neutral_foreground_1`；HC token 中 `palette_yellow_background_3` 与 `neutral_foreground_1` 都是 `#ffffff`，dark 中前者为 `#fde300`、后者为白色。Important 的背景是 `neutral_foreground_1`、前景是 `neutral_foreground_on_brand`；web_dark 中两者也都是 `#ffffff`，源码上存在同样的白底白字风险，但本轮只实际复现了 Warning，没有单独截取 Important。
- **预期**：警告徽标在所有内置主题下文字可辨。
- **实际**：HC 白底白字；dark 白字黄底，对比不足。
- **影响**：任何依赖 Warning Badge 表达状态的界面都会在两种主题下丢失文字信息。它不阻塞便签核心流程；应用改用标题栏文本“编辑中 · 未保存/已保存”，没有把低对比徽标当唯一信号。
- **处置**：本任务不修改组件 spec（不是仅影响本应用、需要单独决定前景映射并补主题测试）；保留为可追踪记录。建议后续按 Fluent 的 `colorPaletteYellowForeground1` 或对比度策略修正，并为 dark/HC 增加 spec 断言。

### I-2（上游 GPUI 文本引擎，未修复）：Textarea 不处理鼠标滚轮

- **复现**：便签应用输入 30 行长正文，指针在正文上滚动滚轮；视图不动、不出现滚动条。按 Ctrl+End 后，视图滚动到末尾并出现滚动条（截图 `notes-body-scrolled2.png` 与 `notes-body-end.png`）。
- **源码依据**：本版 `gpui-base` 的 `InputBaseState::on_scroll_wheel` 只被测试调用，输入元素没有把 `ScrollWheelEvent` 接到该状态。
- **预期**：指针在长正文上滚动应移动视图。
- **实际**：只有光标/键盘移动会滚动视图。
- **影响**：偏好鼠标的用户阅读长正文不便；键盘仍可用。应用没有额外包一层滚动容器来掩盖该缺口。
- **处置**：属于固定版本的上游文本引擎能力，当前不能在本仓库公开边界内直接修复；记录为已知限制，建议在后续 GPUI 快照评估时复查。

### I-3（应用，已修复）：长标题在窄窗口撑破标题栏与状态栏

- **复现**：140 个字符的标题 + 约 520 逻辑像素宽窗口；标题栏“当前：…”和状态栏右侧信息被右边缘裁切。
- **预期**：文本省略，工具栏/状态栏不越界。
- **实际**：修复前无截断，内容裁切到窗口外。
- **处置**：标题栏右侧改为 `flex_1 + min_w(0) + truncate + text_right`；窄窗口使用短提示和 `标题 / 正文 字` 计数；宽窗口隐藏冗余的“N 条便签 · 内存模式”。在 `notes-final-narrow.png` 复核。

### I-4（应用，已修复）：初始窗口尺寸未按显示器可见区域限幅

- **复现**：默认 1180×760 逻辑像素；在更小的可用区域（例如 1366×768 或高缩放的笔记本）可能超出工作区。
- **预期**：初始窗口落在当前显示器可见区域内。
- **实际（修复前）**：直接使用固定尺寸。
- **处置**：读取 `primary_display().visible_bounds()`，按可用宽高减边距限幅，并保留 720×480 的最小值；本机 150% 显示器上 1180×760 本来就放得下，因此没有可见尺寸变化。

### I-5（应用，已修复）：菜单“取消修改”恢复内容但不关闭菜单

- **复现**：输入草稿，打开“更多”菜单，按 Down Down 到“取消修改”，Enter 激活。内容恢复，但菜单仍然打开；“取消修改”因为不再脏而变为禁用，焦点留在菜单面板内。
- **预期**：与保存、置顶、删除一致，激活后关闭菜单，焦点回到打开菜单前的元素。
- **实际（修复前）**：`cancel()` 只恢复输入并通知重绘，没有清 `menu_open`；`MenuDropdown` 不会在 item 激活后自动关闭。
- **影响**：菜单遮挡编辑器，且焦点没有沿其他菜单动作的路径归还；用户需要额外按 Esc 或点击外部。
- **处置**：`cancel()` 显式设置 `self.menu_open = false`，与 `save()` / `set_pinned()` 一致。新增 `menu_cancel_restores_the_draft_closes_and_returns_focus`：脏状态下 Down Down Enter，断言内容恢复、菜单关闭、标题焦点归来。定向移除这一行后测试在 `Cancel must close the menu; MenuDropdown does not auto-close` 失败；恢复后通过。真实窗口见 `menu-cancel-real.png`。

### I-6（应用测试，已修复）：设置浮层的 Tab 陷阱测试不足以证明循环

- **复现**：原 `popover_focus_cycle_stays_inside_the_panel` 只按一次 Tab、一次 Shift+Tab，并断言 `settings_focus.contains_focused`。普通焦点遍历同样可能满足；它也从未证明焦点在控件间移动，或末项/首项互相环绕。
- **预期**：断言焦点句柄确实改变；覆盖面板→首项、末项→首项、首项→末项，并在多轮 Tab 中始终不进入标题/正文。
- **实际（修复前）**：测试只覆盖“仍在面板内”；且设置/属性/菜单三个浮层容器的 `FocusHandle` 被标成 tab stop，Tab 循环里会多出一个无视觉焦点的面板容器停靠点。
- **处置**：三个浮层容器改为普通 `cx.focus_handle()`（仍可被程序化聚焦，但不再进入 Tab 顺序；触发按钮仍是停靠点）；`settings_popover_wraps_tab_between_controls` 逐次比较 `window.focused()` 的句柄，收集完整循环，断言每次移动、循环长度至少 2、容器不在循环中、末项 Tab 回首项、首项 Shift+Tab 回末项，并再走两轮确认不进入背景输入。
- **变异验证**：临时移除 `popover.rs` 的 `.focus_trap(...)` 后，该测试在 `Tab escaped the open settings panel` 失败；恢复后通过。真实窗口：`settings-tab1/8/9.png` 与 `settings-esc-focus.png`。
