# 窗口材质（Mica）：从"调用成功"到"真的透出来"

2026-11-16，Windows 11 25H2 build 26200，150% 缩放，浅色主题，默认蓝色壁纸。
基线提交 `64e17c6`，本记录对应 T-055 的阶段 A–D，阶段 E 的原生手势仍在未验证项里。

## 问题

`gpui-pre-windows 0.3.10` 的 `set_background_appearance` 先记下请求值再调 DWM，DWM 失败或版本不足时静默返回；它的 getter 因此只能证明"我们请求过"。`FluentRoot` 又始终画 `neutral_background_1` 实色，即使窗口拿到了材质也会被自己的内容遮住。要交付的是"显式启用 + 可靠回退"，所以必须先能分别观察**请求**与**生效**。

## 原生证据（真实窗口）

启用 → 撤销 → 再启用，每一步都打印期望值与 DWM 读回值：

```text
backdrop:request=Mica  result=Applied expected=2 reported=Some(2) ok
backdrop:request=Solid result=Applied expected=1 reported=Some(1) ok
backdrop:request=Mica  result=Applied expected=2 reported=Some(2) ok
backdrop:policy=material:true alpha:0.5 window:MicaBackdrop
```

`expected` 是 DWM 契约里的常量（`DWMSBT_NONE=1`、`DWMSBT_MAINWINDOW=2`、`DWMSBT_TABBEDWINDOW=4`），不是从适配器读回来的值——否则映射写错时会自己和自己相等。

像素（桌面截屏取样，窗口覆盖壁纸）：

| 运行 | 根层 alpha | 窗口内取样 |
|---|---|---|
| Mica | 0 | `(239, 244, 249)` — 非壁纸原色 `(32, 132, 249)`，材质确实在 |
| 实色（`DWMSBT_NONE`） | 0 | `(255, 255, 255)` — 不透明清屏 |
| Mica | 0.5 | `(247, 249, 252)` — 50% 白叠在材质上 |
| 实色 | 1.0 | `(255, 255, 255)` |

第一行是关键：根层 alpha 0 时窗口不是壁纸的颜色，说明 DWM 真的在合成材质，而不是我们的内容画了什么。

## GPUI 回归

`crates/fluent-components/src/root/backdrop_tests.rs` 的 4 条：默认不透明且等于主题底色、测试平台（无合成器）请求 Mica 后仍不透明、`prime(...Applied)` 后根层 alpha 等于 `MATERIAL_LAYER_ALPHA`、高对比度下即使已确认也保持不透明。测试平台没有合成器，所以用 app global 注入"合成器已同意"，注入点只存在于 `#[cfg(test)]`。

破坏矩阵（`target/breakage_mica.py`，逐条 patch → 只跑目标测试 → 还原并 `os.utime`）：

## 图库里的现场演示，以及它测出来的深色缺陷

`crates/fluent-gallery/src/sections/overlays.rs` 新增 `backdrop_section`：`backdrop` 一节的三选一（Solid / Mica / Mica Alt），点选即改 `Gallery::backdrop`，根层重新走 `policy_for`。实测（`FLUENT_GALLERY_SECTION=backdrop`，150% 缩放，桌面截屏取样窗口空白处）：

| 运行 | 主题 | 实测像素 |
|---|---|---|
| 实色 | 浅色 | `(255, 255, 255)` |
| Mica | 浅色 | `(248, 249, 252)` |
| 实色 | 深色 | `(41, 41, 41)` |
| Mica（修前） | 深色 | `(141, 142, 145)` |
| Mica（修后） | 深色 | `(34, 37, 43)` |

深色那两行是本轮唯一由"看图"发现的缺陷：材质在第一版里只请求了 `DWMWA_SYSTEMBACKDROP_TYPE`，没有写 `DWMWA_USE_IMMERSIVE_DARK_MODE`，DWM 因此给出**浅色**材质，再叠 50% 深色层，得到既不像深色材质也不像主题底色的灰面。修法是让 `policy_for` 把主题明暗一起写入，并把明暗并入缓存键——切主题才会重新应用。修复后同一位置为 `(34, 37, 43)`，与深色 Mica 面 `(26, 31, 41)` 相符。

浅色主题下 50% 覆层只让材质露出 3–7 个色阶（上表前两行），这是 Fluent 自己的做法而不是缺陷：`LayerFillColorDefault` 就是半透明白。想看材质本身，用深色主题、或把窗口拖到深色壁纸区域。

## 未验证

- 真实物理手势：拖动、双击最大化、Snap、四边四角缩放（脚本发的是窗口消息，不是指针手势）。
- 系统关闭"透明效果"时 DWM 的行为、窗口失活时的材质观感。
- 高对比度下的材质外观（代码路径会强制退回实色并有单测，观感未截屏）。
- macOS / Linux：`Unsupported` 分支有测试，平台外观未验证。
- 多显示器、缩放比例切换后的材质表现。
- 手动选主题（应用深色 / 系统浅色）与系统材质色调是否一致——当前只保证我们画的那一层与写入的 immersive dark 标记与主题一致。
- 图库三选一的鼠标点选没有自动化：截图用的是启动时的 `FLUENT_GALLERY_BACKDROP`，三条路径共用同一个 `policy_for`。

## 第二次审核：回退只改了页面，没改窗口

审核报了两件事，都在同一句假设上：材质成功才需要动窗口。

### 一、请求失败后窗口没有真的恢复不透明

原来的 `apply` 在拿到平台答复**之前**就调用 GPUI 的 `set_background_appearance(Mica)`。被拒时 `resolve` 确实返回 `window: Opaque`，但根只消费 `policy.layer`，窗口外观仍停在材质分支：页面变成实色，渲染器仍按透明清屏合成。除此之外，GPUI 的 `Opaque` 分支不会清除 `DWMWA_SYSTEMBACKDROP_TYPE`，即使外观设回去了，材质也还挂在窗口上。

现在的顺序是：先把明暗标记与材质写给 DWM 并读回，只有读回等于请求值才把外观切成材质；否则设回 `Opaque` 并显式写 `DWMSBT_NONE`。返回的仍是平台的原始答复，回退成功不会覆盖 `Failed`／`Unsupported`／`Mismatch`，`last_request` 也照原样保留。非 Windows 平台先问再改，拿不到 `Applied` 就不动外观。缓存改成按窗口的 `BackdropRegistry`（键为 `window.window_handle()`），记录 `(请求, 明暗) → 答复`。

### 二、图库选 Solid 没有撤销材质

选项表里 Solid 写的是 `None`，而 `None` 的语义是"没有请求"，渲染时根本不会再走策略，于是旧材质留在窗口上。原生探针实测读回 `2 → 2 → 1 → 2`：中间那次"切到 Solid"什么都没发生。

现在 Solid 写 `Some(WindowBackdrop::Solid)`，`None` 只保留给"还没人选过"，默认窗口因此仍不被接管。映射抽成 `backdrop_for_choice`，由 `sections::overlays::choice_tests` 固定。

### 测试

| 测试 | 断言的可观察结果 |
|---|---|
| `the_default_root_paints_an_opaque_surface` | 没有请求时连平台都不问（`fake_calls()` 为空），根层为实色 |
| `a_refused_material_leaves_the_window_opaque` | 收到的外观调用只有 `Opaque`、显式清除一次、根层 alpha 为 1、`last_request` 保留 `Unsupported` |
| `a_failed_request_keeps_its_reason` | 清除以后 `Failed(-2147467259)` 仍被保留 |
| `a_mismatched_material_is_treated_as_a_refusal` | `Mismatch { asked: 2, reported: 1 }` 同样回退 |
| `a_confirmed_material_turns_the_window_transparent` | 只有 `MicaBackdrop`、不清除、alpha ≈ 0.5 |
| `high_contrast_asks_for_solid_and_stays_opaque` | 请求被降为 `(Solid, false)`、外观 `Opaque`、alpha 为 1 |
| `a_repaint_does_not_ask_the_compositor_again` | 四帧重绘只产生一次平台调用 |
| `solid_removes_the_material_and_mica_can_come_back` | 请求序列 Mica→Solid→Mica，外观序列跟着变，根层实色↔半透明 |
| `the_dark_flag_is_part_of_the_request` | 深色首次 `(Mica, true)`，切浅色后 `(Mica, false)` |
| `choosing_solid_asks_for_solid_rather_than_for_nothing` | 索引 0 得到 `Some(Solid)`，未知索引得到 `None` |

这些断言看的是**发给窗口的调用**，不是策略值，也不是背景色：测试平台的外观 setter 是空操作，只断言颜色会让"页面变实色、窗口还透明"照样通过。为此 `backdrop.rs` 有一个只在 `cfg(test)` 存在的记录平台，生产路径原样运行，未安装时不改变任何行为。

### 原生往返（Windows 11 25H2 26200，150%）

探针 `titlebar_probe backdrop` 现在走 Mica → Mica Alt → Solid → Mica，每一步都与 DWM 契约里的值比较：

```text
backdrop:request=Mica result=Applied expected=2 reported=Some(2) ok
backdrop:request=MicaAlt result=Applied expected=4 reported=Some(4) ok
backdrop:request=Solid result=Applied expected=1 reported=Some(1) ok
backdrop:request=Mica result=Applied expected=2 reported=Some(2) ok
```

图库界面也走了一遍同样的链路：`FLUENT_GALLERY_BACKDROP=mica`、`FLUENT_GALLERY_SECTION=backdrop` 启动，用 `SetCursorPos` + 鼠标事件点三个单选，再用 `DwmGetWindowAttribute(hwnd, DWMWA_SYSTEMBACKDROP_TYPE)` 读回同一窗口：`2 → 4 → 1 → 2`。日志里对应的四次策略更新为 `Mica ← None`、`MicaAlt ← (Mica, false)`、`Solid ← (MicaAlt, false)`、`Mica ← (Solid, false)`，即缓存确实按请求推进，没有漏发也没有多发。

### 仍未验证

- 物理手势（拖动、双击、Snap、四边四角缩放）与 macOS／Linux 的材质与标题栏，仍按[标题栏验证边界](../subsystems/titlebar.md)逐项手工确认。
- 关闭系统"透明效果"、失活窗口、深色壁纸下的材质观感没有做像素对照；材质是否出现还取决于合成器策略，读回值只证明请求被接受。
- 多显示器、运行时切换缩放比例重新应用材质的路径没有实测。
- 图库点击验证里，启动后的第一次点击偶尔只激活窗口而不落到单选（脚本层现象），因此在脚本里重复点击确认；真实用户点击不受影响，但这条没有作为产品行为断言。
